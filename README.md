# E-Cell SMVIT website

A redesign of https://www.ecellsmvit.in/ built for the E-Cell Executive web development task:
landing page (hero + footer), signup, login and a member dashboard.

**Flow:** Landing page → Sign up / Log in → Supabase Auth → Dashboard (with a welcome toast).

- **Hosting:** Vercel (static site, one small build step)
- **Auth and database:** Supabase (email + password auth, a `profiles` table with row-level security)
- **Frontend:** plain HTML, CSS and JavaScript, no framework

## Project structure

```
public/                  Everything Vercel serves
  index.html             Landing page: hero with the interactive "venture curve", about, programs, team, footer
  signup.html            Sign-up form (name, email, optional VTU USN, password + strength meter)
  login.html             Log-in form
  dashboard.html         Signed-in page: welcome message, member pass, founder checklist, log out
  css/styles.css         All styles; colour and type tokens at the top, light and dark themes
  js/auth.js             Supabase client and auth helpers shared by every page
  js/auth-page.js        Form validation and submit for login/signup
  js/main.js             Landing page interactions (curve, team list, IST clock)
  js/dashboard.js        Dashboard guard, greeting and checklist (saved to the member's profile)
  js/config.js           Generated by the build (git-ignored)
  js/vendor/supabase.js  Copied from node_modules by the build (git-ignored)
scripts/build.js         Writes js/config.js from env vars and copies supabase-js
supabase/migrations/     SQL for the profiles table, RLS policies and signup trigger
vercel.json              Build command, output folder and security headers
```

## Environment variables

| Name | Where to find it |
|---|---|
| `SUPABASE_URL` | Supabase dashboard → Project Settings → API → Project URL |
| `SUPABASE_ANON_KEY` | Same page → the **publishable** key (`sb_publishable_…`) or the legacy `anon` key |

Both are safe to ship to the browser; row-level security protects the data. Never use the `service_role` / secret key here.

## Run locally

```bash
npm install
cp .env.example .env    # fill in the key, then:
export $(cat .env | xargs) && npm run dev    # http://localhost:3000
```

`npm run build` stops with a clear message if either variable is missing.

## Deploy

1. **Supabase**: the project `ecell-smvit` already has the migration in `supabase/migrations/` applied.
   In Authentication → URL Configuration, set **Site URL** to your Vercel domain and add
   `https://<your-domain>/dashboard.html` to **Redirect URLs**.
2. **Email confirmation**: by default Supabase asks new members to confirm their email, and the
   built-in mailer only sends a few emails per hour. The site handles both modes:
   - Confirmation **on**: signup shows "Check your inbox"; the link signs the member in on the dashboard.
   - Confirmation **off** (Authentication → Sign In / Providers → Email → Confirm email): signup goes straight to the dashboard.
   For real use with confirmation on, add your own SMTP sender in Authentication → Emails.
3. **Vercel**: import the GitHub repo, keep the framework preset as "Other", add the two environment
   variables above, and deploy. `vercel.json` sets the build command and output folder.

## How authentication works

- Signup calls `supabase.auth.signUp` with the member's name and USN as metadata. A database trigger
  (`handle_new_user`) creates their `profiles` row and member ID (`ECS-<year>-<6 hex>`).
- Login calls `signInWithPassword`; Supabase handles password hashing, sessions and rate limits.
- `profiles` has row-level security: a member can read only their own row and can update only the
  `checklist` column. Name, USN and member ID can't be changed from the browser.
- The dashboard checks for a session and sends signed-out visitors to the login page. The data it shows
  is protected by RLS, so the page itself holds nothing private.
- Validation rules match on the client and in the database (`USN` format, name length).
